# XquiX Studio — Parent Experience Migration ## Objective Migrate the existing **Parent Experience / Water Polo 1×1 tutorial** from the older Parent Experience HTML file into the **current production version of XquiX Studio**. The Parent Experience must no longer exist as a separate fork of an older XquiX Studio. Instead: > **Parent Experience becomes a module/mode inside the current XquiX Studio architecture.** The current XquiX Studio must remain the **single source of truth** for the field, players, ball, interaction systems, UI architecture, mobile behavior, storage, authentication, Game Tracker, and all future shared functionality. The goal is to preserve the existing Parent Tutorial content and interactions while replacing its dependency on the old Studio engine with the corresponding systems of the current XquiX Studio. --- # 1. CRITICAL DEVELOPMENT RULE **Do not merge the old Parent Experience file wholesale into the current XquiX Studio.** The Parent Experience file was built from an older XquiX Studio version and therefore contains outdated versions of shared Studio systems. We want to extract only the functionality that is genuinely specific to the Parent Experience. Do NOT overwrite or downgrade current XquiX Studio functionality with code from the Parent Experience file. When functionality already exists in the current Studio, the Parent Experience must use the current implementation. --- # 2. FIRST STEP — MIGRATION AUDIT Before changing production code, compare: **SOURCE:** Current Parent Experience HTML **TARGET:** Latest XquiX Studio HTML Create a migration inventory with three classifications. ### A — Parent-Specific Functionality — MIGRATE Identify functionality belonging specifically to the Parent Experience, including: * `PX` namespace * Parent Experience state * Parent start screen * lesson definitions * lesson/storyboard content * lesson navigation * tutorial overlays * instructional text * interactive lesson validation * lesson-specific highlighting * lesson-specific player positioning * referee tutorial elements * shot clock tutorial behavior * shooting interactions * lesson completion logic * skip lesson functionality * restart functionality * tutorial progress state * Parent-specific cleanup routines * Parent-specific free-play transition * Parent-specific UI restrictions * 2-Minute Experience, if currently contained in the Parent system * any Parent-specific touch/mobile behavior that is not already handled by the current Studio Preserve these unless they are clearly obsolete. ### B — Shared Studio Functionality — REPLACE WITH CURRENT ENGINE Identify anything in the Parent file that duplicates functionality already present in the latest XquiX Studio. Examples may include: * field rendering * player creation * player movement * player rotation * ball handling * goals * field geometry * shooting mechanics * camera/view handling * drawing systems * text boxes * Team Manager * context menus * save/load * presentation mode * touch handling * mobile layout * general overlays * authentication * subscription/authorization systems * storage * current UI components Do NOT migrate these older implementations. Connect the Parent Experience to the equivalent current Studio functionality instead. ### C — LEGACY / REDUNDANT CODE — REMOVE Identify code that exists only because Parent Experience was developed as a standalone fork of the old Studio. Do not migrate this code if it is no longer required once Parent Experience runs inside the current Studio. --- # 3. PROVIDE THE AUDIT BEFORE MAJOR REFACTORING Before executing the full migration, provide a concise report showing: | Parent System | Existing Parent Function | Current Studio Equivalent | Action | | -------------------- | ------------------------ | ------------------------- | ----------- | | Field | old field engine | current field engine | use current | | Player movement | old movement logic | current player engine | use current | | Lesson engine | PX lesson system | none/shared partial | migrate | | Tutorial overlays | PX-specific | — | migrate | | Game Tracker handoff | PX callback | current Game Tracker | connect | Continue this inventory for all meaningful Parent Experience systems. Flag any Parent functionality that cannot cleanly map onto the current Studio before changing its behavior. --- # 4. TARGET ARCHITECTURE The final architecture should conceptually become: **XquiX CORE** Shared systems: * Field Engine * Player Engine * Ball Engine * Interaction Engine * Animation * Touch/Mobile * Shared water-polo logic * Storage * Authentication * Authorization Using this common core: ### Coach Studio Existing professional coaching functionality. ### Parent Experience * Parent Home * Water Polo in 2 Minutes * Water Polo 1×1 * Parent Free Explore ### Game Tracker * Game tracking * player statistics * goalkeeper statistics Do not create separate copies of the field/player/ball engine for these modes. --- # 5. CREATE A CLEAR PARENT MODE Parent Experience should have an explicit application state such as conceptually: `appMode = "parent"` with appropriate sub-modes such as: * `parent-home` * `parent-quickstart` * `parent-tutorial` * `parent-explore` * `game-tracker` Use the current architecture if an equivalent mode/state system already exists rather than creating a competing system. Parent Mode should control which tools and UI elements are available without modifying the underlying shared engine. --- # 6. PARENT HOME Do not force users directly into the tutorial. Create/prepare the Parent Experience so its entry point can eventually offer: ### Water Polo in 2 Minutes Quick introduction for completely new parents. ### Water Polo 1×1 Full interactive Parent Tutorial. ### Game Tracker Allow parents to begin tracking a game immediately. ### Explore the Field Allow parents to interact with the simplified XquiX field without completing the tutorial. The tutorial should therefore be **recommended, not mandatory**. A parent must be able to access Game Tracker before completing Water Polo 1×1. --- # 7. PRESERVE TUTORIAL CONTENT The educational content and intended interactions of the existing Parent Experience should remain unchanged during this migration unless a technical incompatibility requires modification. This is primarily an **architectural migration**, not a redesign of the Parent Tutorial. Do not rewrite: * lesson wording * lesson sequence * teaching philosophy * rule explanations * interactions * storyboard unless specifically requested. If an existing interaction cannot be reproduced using the new engine, flag it rather than silently changing the lesson. --- # 8. BUILD AN ADAPTER LAYER WHERE NECESSARY The Parent Tutorial currently calls functions based on the older Studio implementation. Where practical, do not rewrite every lesson individually. Instead, create a small Parent-to-Core adapter/API layer so tutorial commands can call the current Studio engine. Conceptually: `PX.movePlayer(...)` → current XquiX player movement `PX.setBall(...)` → current XquiX ball engine `PX.setView(...)` → current view/camera system `PX.resetScene(...)` → current Studio scene reset `PX.highlightPlayer(...)` → Parent-specific overlay using current player object This should minimize duplication and make future Studio improvements automatically available to Parent Experience. --- # 9. GAME TRACKER INTEGRATION The existing Parent Experience already anticipates a handoff to Game Tracking. Preserve this concept, but connect it directly to the **current Game Tracker implementation**. The Parent Experience must not contain a separate Game Tracker implementation. Desired behavior: Parent Home → Game Tracker or: Water Polo 1×1 → Exit / Skip → Parent Home → Game Tracker or: Water Polo 1×1 completed → Continue to Game Tracker / Explore / Parent Home Switching modes should cleanly remove tutorial overlays and tutorial-specific event listeners without rebuilding or reloading the entire XquiX application if that is technically avoidable. --- # 10. CLEANUP IS CRITICAL The existing Parent Experience contains significant lesson-specific state and cleanup logic. During migration, verify that leaving a lesson removes: * temporary players * temporary balls * tutorial arrows * tutorial highlights * referee graphics * shooting targets * temporary clocks * event listeners * lesson overlays * timers * animation loops * temporary CSS classes * Parent-only controls No Parent Tutorial state should leak into Game Tracker or Coach Studio. Likewise, entering Parent Experience should not damage existing Studio state. --- # 11. DO NOT DUPLICATE FEATURES Before implementing any function needed by Parent Experience: 1. Search the current XquiX Studio for an existing implementation. 2. Reuse it if available. 3. Extend it if a small extension solves the Parent requirement. 4. Only create a Parent-specific implementation if the behavior genuinely belongs exclusively to Parent Experience. Follow the principle: > **One engine. Multiple experiences.** --- # 12. PRESERVE CURRENT XQUIX STUDIO The current Studio has priority over the Parent prototype. Do not remove, simplify, or modify current Studio functionality merely to make the Parent Experience compatible. If Parent Experience expects old behavior that conflicts with the current Studio architecture, adapt the Parent Experience. Do not adapt the current Studio backwards. --- # 13. MIGRATION SEQUENCE Execute the work in controlled phases: ### Phase 1 — Audit Map Parent-specific, shared, and obsolete functionality. ### Phase 2 — Extract Separate Parent-specific CSS, state, lesson data, UI and interaction logic from old shared Studio code. ### Phase 3 — Integrate Introduce Parent Mode into the latest XquiX Studio. ### Phase 4 — Adapter Connect existing PX lesson commands to current XquiX Core functions. ### Phase 5 — Parent Home Create the entry structure for: * 2-Minute Experience * Water Polo 1×1 * Game Tracker * Explore ### Phase 6 — Validate Lessons Test every currently implemented Parent lesson individually. ### Phase 7 — Validate Mode Switching Test: Parent → Tutorial Parent → Game Tracker Tutorial → Parent Home Tutorial → Game Tracker Game Tracker → Parent Home Parent → Explore Explore → Parent Home ### Phase 8 — Remove Legacy Dependencies Only after successful validation, remove old Parent-file dependencies that have been replaced by current XquiX Core systems. --- # 14. REGRESSION TESTING After integration verify that existing Coach Studio functionality remains unchanged. Specifically test important current systems including: * moving players * player rotation * ball possession * Smart Ball functionality * formations * sequences * drawing * Team Manager * Presentation Mode * touch/mobile behavior * saving/loading * authentication * authorization * Game Tracker * any current role/subscription logic Parent Experience integration must not introduce regressions into the professional Studio. --- # 15. CODE ORGANIZATION Even if XquiX Studio currently remains a single HTML application, organize the new code into clearly marked logical sections such as: `XQUIX CORE` `PARENT EXPERIENCE — STATE` `PARENT EXPERIENCE — LESSON DATA` `PARENT EXPERIENCE — UI` `PARENT EXPERIENCE — INTERACTIONS` `PARENT EXPERIENCE — CORE ADAPTER` `PARENT EXPERIENCE — CLEANUP` `GAME TRACKER` Avoid scattering PX code throughout unrelated Studio functions unless integration genuinely requires it. The objective is to make eventual physical separation into modules/files straightforward when XquiX later moves further toward a backend/modular architecture. --- # 16. IMPORTANT — DO NOT OVER-OPTIMIZE DURING MIGRATION Do not simultaneously redesign or heavily optimize the Parent Tutorial. First achieve functional equivalence on the current XquiX engine. After successful migration and regression testing we can separately: * optimize code * continue building remaining lessons * improve Parent Home * add persistent tutorial progress * connect accounts * develop Parent-specific authorization * expand Game Tracker * add additional Parent tools Migration first. Enhancement second. --- # SUCCESS CRITERIA The migration is successful when: 1. The current XquiX Studio remains fully functional. 2. Parent Experience runs inside the latest XquiX Studio. 3. The Parent Tutorial no longer depends on the old Studio engine. 4. Existing Parent lessons behave as they did before migration. 5. Parent users can enter Game Tracker without completing the tutorial. 6. Tutorial completion can hand the user into other Parent functions. 7. Parent Experience and Game Tracker use the same current XquiX field/player/ball systems. 8. No duplicate legacy field engine remains necessary for Parent Experience. 9. Parent-specific state is properly cleaned when switching modes. 10. Future Parent lessons can now be developed directly against the current XquiX architecture. **Do not begin adding new Parent lessons until this migration has been completed and validated.**
